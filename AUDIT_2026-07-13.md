# Workstream A — Silent wrong numbers (P0: shipping bad data today)

## A1. [CRITICAL] `return_1d` is always 0.0; `return_5d/20d/60d/90d` off-by-one
**Status:** Open
**Files:** `indicators.py:718-721` (`pct_return`), consumed at ~:969 and across `js/pages/recommendations.js`, `js/analysis.js`, `routes/learning.py`, `js/prompts.js`

`pct_return(days)` does `close.iloc[-1] / close.iloc[-days] - 1`. For `days=1` numerator and denominator are the same element → identically `0.0`. Every longer window spans `days-1` gaps, not `days` (a "5-day return" is really 4-day). Contrast `_score_ticker()`'s own `ret_5d` at ~:535 which correctly uses `closes[-6]` (`-period-1`) — two inconsistent return conventions coexist in one file.

**Fix:** `return safe_float((close.iloc[-1] / close.iloc[-days-1] - 1) * 100)` and guard `if len(close) > days + 1`. Audit every consumer of `return_1d` for downstream assumptions (it feeds prompt context, the Signals page, and `capital_efficiency`/`avg_pnl_per_day` math in `learning.py`).
**Test:** `indicators.py` unit test — synthetic monotonic series where `close[-2]→close[-1]` is +5%, assert `return_1d ≈ 5.0` (currently returns 0.0); assert `return_5d` spans exactly 5 trading days.
**Effort:** S (1-line fix, but wide blast radius on consumers — audit before shipping).

## A2. [HIGH] RSI returns neutral 50 instead of 100 when `avg_loss == 0`
**Status:** Open
**Files:** `indicators.py:259-266` (`compute_rsi`), consumed at ~:724

`rs = avg_gain / avg_loss.replace(0, np.nan)` → `NaN` when avg_loss is 0 → RSI `NaN` → `safe_float(rsi.iloc[-1], 50)` silently coerces to neutral 50. Standard convention: all-gains window ⇒ RS→∞ ⇒ RSI = 100 (extreme overbought). Hides a genuine overbought signal on young/strong series.

**Fix:** after computing `rs`, set RSI = 100 where `avg_loss == 0 and avg_gain > 0`, and RSI = 50 (or 0) where both are 0 (flat). Do it explicitly, not via NaN-coercion.
**Test:** all-up-days window ⇒ RSI == 100; flat window ⇒ RSI == 50; normal window unchanged.
**Effort:** S.

## A3. [MEDIUM] `sector_rs_5d` compares misaligned windows before ASX settlement
**Status:** Open
**Files:** `indicators.py:883-895`

The ticker `close` series passes through `_drop_forming_bar()`/`_sanity_check()` (:608-609), so before the settlement cutoff its last bar is yesterday's settled close. But `etf_hist = etf_stk.history(period='1mo', ...)` (:889) is fetched raw with no forming-bar guard, so it still carries today's partial intraday bar. `ticker_ret5` ends yesterday; `etf_ret5` ends on today's partial → a one-day lookback misalignment injecting intraday noise into a signal fed straight into the Claude prompt and Signals page whenever run during market hours.

**Fix:** apply the same `_drop_forming_bar()` (and ideally `_sanity_check`) to `etf_hist` before computing `etf_ret5`, so both legs end on the same settled bar. Confirm both `.iloc[-1]`/`.iloc[-6]` reference identical trading dates.
**Test:** feed a ticker series ending yesterday and an ETF series whose last bar is "today partial"; assert both returns computed over the same date span (mock the guard).
**Effort:** S.

## B2. [CRITICAL] `applyRegimeModifiers()` rescales `qty` but not `riskAUD`/`rewardAUD`/`evNet`
**Status:** Open
**Files:** `js/regime-engine.js:179-183`; consumers `js/analysis.js` `_applyHeatBudget` (~:54-87), rec-card render, `_recomputeBuyEv` (~:1614-1625)

Non-panic branch scales `out.qty *= sizeMult` but leaves `riskAUD/rewardAUD/evNet` at pre-scale values. Two failure modes:
1. **`trend` (sizeMult 1.1) or blended >1.0:** qty scaled UP past the Kelly/1%-risk/20%-position/5%-liquidity caps `computeTradeParams()` proved, while `riskAUD` stays smaller → actual dollar risk silently exceeds the hard caps AND `_applyHeatBudget()` under-counts consumed risk → aggregate portfolio heat cap can be breached invisibly.
2. **`riskOff/highVol/sideways` (0.5/0.6/0.8):** qty shrinks correctly but `riskAUD/rewardAUD` stay inflated → the rec card and heat-budget gate operate on a risk number that no longer matches position size; unrelated recs get needlessly blocked/scaled by an inflated running total.

`FIXES.md #15`'s `_recomputeBuyEv()` only refreshes `expectedProfit/netProfit` for `_netProfitEngine` recs — it never re-derives `riskAUD` from qty. Compare `js/analysis.js:30-36` `_applyCorrSizing`, which DOES recompute `riskAUD` in the same step it scales qty (the correct pattern).

**Fix:** in `applyRegimeModifiers()` non-panic branch, after scaling qty, recompute proportionally: `out.riskAUD = round(out.riskAUD * sizeMult)`, `out.rewardAUD = round(out.rewardAUD * sizeMult)`, and refresh `evNet` (fixed brokerage means EV is not linear in qty — recompute from the new qty via the same helper, don't just scale). Preferred: converge on ONE `_rescaleRecQty(rec, mult)` helper shared by `_applyCorrSizing` and `applyRegimeModifiers` so the qty↔risk fields never drift again.
**Test:** vitest — `applyRegimeModifiers` on `riskOff` halves qty AND `riskAUD`; on `trend` the post-scale `riskAUD` still respects `maxRiskBudgetPct`.
**Effort:** M.

# Workstream D — Indicator / earnings correctness (P1/P2)

## D1. [HIGH] `pre_earnings_risk` is False on the earnings day itself
**Status:** Open
**Files:** `indicators.py:~842/846/849`

`days_to_earnings = (Timestamp(first).replace(tzinfo=None) - Timestamp.now()).days`. `first` is a midnight-normalized date; `now()` carries time-of-day. On the earnings date, any time after 00:00 makes the delta negative → `.days` floors to `-1` → fails the `0 <= days_to_earnings <= 14` gate exactly on the highest-risk day. `earningsAdj` defaults to 1.0 instead of 1.3 (gotcha #28) and the "📅 Pre-earnings" badge is suppressed on event day.

**Fix:** compare dates, not datetimes — normalize `now()` to midnight (`Timestamp.now().normalize()`) or compute `(first_date - today_date).days` on `.date()` objects. Preferably use Sydney date (`_sydney_now()`, cf. gotcha #87) to avoid a UTC-vs-AEST off-by-one at the day boundary.
**Test:** earnings date == today ⇒ `days_to_earnings == 0` and `pre_earnings_risk == True`; earnings tomorrow ⇒ 1; earnings yesterday ⇒ negative and False.
**Effort:** S.

# Workstream E — Learning-loop statistical integrity (P1/P2)

## E1. [HIGH] Circular `skill_score` inflates the decay-weighted win rate (self-reinforcing loop)
**Status:** Open
**Files:** `routes/learning.py:356-445` (`compute_skill_score_deterministic`), `:4224-4231` + `_compute_phase8_meta` (Mann-Whitney gate), `_weight()` ~:4014-4020

`win` (:386) is derived from the outcome (`pnl > 0`), and the score table (:388-398) gives a win 1-2 points more than a loss for the identical `thesis_verdict` (validated 8.0/6.0, irrelevant 5.5/4.0, invalidated 3.0/2.0, etc.). The Phase-8 gate then runs Mann-Whitney comparing `skill_score` between wins and losses to decide "do scores predict outcomes" — but the score is partly *defined by* the outcome, so the test is near-tautological and trips `z>1.28` regardless of genuine skill. Once active, `_weight()` uses that same score (`sf = skill_score/5.0`, clamped 0.2-1.8) to up-weight wins / down-weight losses in every `_wwr()` → a mediocre 45% raw WR can present >50%, pushing the calibration block toward unwarranted "size up" nudges. Exactly the "confidently nudge toward more risk on noise" failure mode.

**Fix (decouple score from outcome for the gate):** the Mann-Whitney predictiveness test must use a skill component that is NOT a function of the realized win/loss — e.g. score the *thesis_verdict + process tags + calibration-at-entry* only, and test that against outcome. Simplest correct change: split `skill_score` into (a) a **process** score (verdict/tags/confidence-honesty, outcome-independent) used for the Phase-8 gate and `_weight()`, and (b) keep the outcome-blended score for display only. Re-run the gate on the process score. Alternatively, disable outcome-weighting of the WR entirely when the only "skill" signal is outcome-derived (guard: if score variance is explained by outcome, treat `sf=1.0`).
**Test:** construct a set where wins and losses have identical process/verdict/tags; assert Phase-8 does NOT activate (currently it does) and `_wwr` equals the unweighted WR.
**Effort:** L (touches the weighting core — needs care + fixture-heavy tests).

## E2. [HIGH] Calibration cache key omits regime-flip params → wrong block served for 5 min
**Status:** Open
**Files:** `routes/learning.py:~4826` (cache key), `_calib_compute` flip handling ~:3957-3983

`_calib_compute` output depends on `flipped_at`/`flipped_to` (halves decay half-life, appends `⚠REGIME_FLIP`), but the 5-min TTL cache key is `(regime, sectors, tickers, days, deep)` only. Whichever caller populates the cache first — with or without flip params — is served to all callers for the window. Right after a flip, a flip-aware request caches the discounted/flagged block, then a non-flip caller within 5 min silently gets the penalty applied to a request it doesn't apply to (or vice versa).

**Fix:** add `flipped_at`/`flipped_to` (bucketed — e.g. round `flipped_at` to the minute) to the cache key tuple. Confirm no other request-varying input is missing from the key.
**Test:** two `learning_calibration` calls differing only in flip params return different blocks (not the cached first).
**Effort:** S.

## E3. [MEDIUM] Several nudges bypass the module's own CI/ESS gate
**Status:** Open
**Files:** `routes/learning.py` — RR-accuracy nudge :4396-4401, top-error nudge :4410-4460, strategy-decay nudge :4364-4394

The file gates most nudges on Wilson-CI + ESS, but:
- RR-accuracy fires on `len(hi_rr) >= 5 and hi_wr < 0.50` with **no CI/ESS** — a 2W/3L fluke (40% vs 50%) triggers "widen stops".
- Top-error fires on raw count + `top_pct >= 0.33` with no significance test on the proportion (only the `stop_too_tight` sub-case self-suppresses); every other tag can fire from 4-of-12 noise.
- Strategy-decay uses `global_delta < -0.15` raw point estimate, no CI.

**Fix:** route all three through the same Wilson-lower-bound / ESS gate the band and correlation nudges use (`_ci_excludes`, `_ESS_MIN`, `_MIN_NUDGE_N`). For RR/strategy-decay, require the CI of the adverse bucket to exclude the comparison rate before emitting.
**Test:** a 2W/3L RR bucket emits NO nudge; a decisively-below bucket at n≥12 still does.
**Effort:** M.

## E4. [MEDIUM] No multiple-comparisons correction across ~10-15 simultaneous tests
**Status:** Open
**Files:** `routes/learning.py` `_calib_compute` (whole)

A single call runs on the order of 10-15 individually-95% tests (3 bands, regime, N sectors, decay, RR, top-error, success-tag, cluster-loss, corr-drag, up to 5 tickers) against the same overlapping ≤300-row sample. Family-wise false-positive ≈ 1-0.95^12 ≈ 46% → more likely than not that at least one nudge per call is a fluke.

**Fix:** apply a Holm-Bonferroni (or Benjamini-Hochberg FDR) correction across the nudges emitted in one compute, OR tighten the per-test bar (e.g. Wilson at 99% for the exploratory nudges) and cap the number of nudges emitted per call to the top-k by effect size. Document the chosen family and α. This is a statistical-design change — pair with E1/E3 so the gate story is coherent.
**Test:** with random-noise outcomes, assert the expected number of spurious nudges per call drops materially vs current.
**Effort:** L (design decision + broad test rework — sequence LAST in this workstream).

## E5. [MEDIUM] HOLD-outcome horizon/bar-count mismatch
**Status:** Open
**Files:** `routes/learning.py` `_resolve_hold_outcomes` — `_HOLD_MIN_BARS=10` :3173, endpoint read `closes.iloc[1:_HOLD_HORIZON_DAYS+1]` :3287, threshold `sqrt(_HOLD_HORIZON_DAYS)` :3189

The length gate requires only ≥10 bars but the vol-scaled miss threshold is always sized for `sqrt(20)` and the endpoint is read at bar 20. A HOLD resolved with 12 bars gets its "day-20 endpoint" off bar 11 while judged against a 20-day-drift threshold → thin/gappy histories get non-uniform effective horizons under one threshold, biasing the miss rate feeding the CI-gated `⚠HOLD_TOO_PASSIVE` nudge.

**Fix:** either (a) require the full `_HOLD_HORIZON_DAYS` bars before resolving (raise `_HOLD_MIN_BARS` to the horizon, mark `<horizon` as `virtual_open`), or (b) scale the threshold to the *actual* number of forward bars used (`sqrt(n_bars_used)`) and read the endpoint at the actual last available bar. (a) is simpler and matches the documented "endpoint over the first H bars" intent.
**Test:** a HOLD with 12 forward bars stays `virtual_open` (option a) OR is judged against a `sqrt(12)`-scaled threshold (option b), not `sqrt(20)`.
**Effort:** S.
