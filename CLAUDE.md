# CLAUDE.md — Sloth ASX Trader

Operator handbook for Claude Code sessions in this repo. Keep this updated when major architecture changes land.

## What this app is

A local-only decision-support tool for Australian equity trading. No SaaS, no cloud DB.
- **Backend:** Python Flask (`asx_server.py`) on `localhost:5000`. Fetches market data via `yfinance`. Persists everything in SQLite (`asx_trader.db`, WAL mode).
- **Frontend:** Vanilla JS single-page app (`asx_trading.html`). Talks to backend, calls Anthropic API directly from the browser, renders with `<canvas>` (no chart libraries).
- **AI:** Claude Sonnet 4.6 for analysis, recommendations, day trading; Gemini for ASX announcements; local Ollama for news + internal "debate" pre-analysis + optional local portfolio analysis via `POST /api/debate/quick-analysis` (opt-in via Settings).

## Run instructions

```bash
pip install -r requirements.txt

# Dev (single-worker, autoreload-free)
python asx_server.py
# Then open asx_trading.html in a browser.

# Production-grade (multi-threaded) — Windows
python waitress_server.py

# Production-grade (multi-worker) — Linux / macOS only
# gunicorn uses fcntl which is POSIX-only and does NOT work on Windows
pip install gunicorn
gunicorn -c gunicorn.conf.py 'asx_server:app'
```

API key options (one of these is required for analysis):
1. **Direct mode (default)**: paste Anthropic key in Settings → kept in `localStorage`.
2. **Proxy mode (opt-in)**: `POST /api/claude/settings {api_key}` once; set `state.settings.useBackendProxy = true`. Key is written to a git-ignored `claude-api.txt` at the repo root (never touches the browser, never committed) — file-based on purpose so the key survives a DB reset/recovery; falls back to the legacy SQLite `settings` row for keys saved before Sprint 72.

Tests:
```bash
python test_app.py        # all Python tests (backend + frontend syntax/function checks)
npm run test:js           # Vitest suite — 160 JS unit tests for pure engine files
```

## Architecture — AI pipeline

Every recommendation flows through four deterministic layers:

```
Signals (indicators.py) ──► Regime gate (regime-engine.js) ──► Claude ──► Quant engine (quant-engine.js) ──► Validator (response-validator.js) ──► UI
                            (deterministic)                   (LLM)      (deterministic)                    (deterministic)
```

| Layer | Job |
|---|---|
| **Regime engine** | Classifies macro (`riskOn/riskOff/panic/highVol/trend/sideways`) from live data; gates which strategies are allowed; applies size modifiers. Panic regime returns `sizeMult=0` → `_regimeBlocked` flag, recs are dropped. Each regime now carries a `stopAtrMult` (2.5–4.0×) and a `_blendedSizeMult` that linearly transitions over 30 min after a flip to prevent cliff-edge sizing. SPI200 futures (`spiChg`) vote in the classifier as a same-session lead indicator. |
| **Claude** | Qualitative conviction only — what to buy/sell and why. Never does arithmetic. User message always includes `TAX_LOSS_HARVEST_ACTIVE` (bool), date, time, and current regime. |
| **Quant engine** | Deterministic sizing: Kelly + vol scalar + multi-constraint (account-risk %, max-position %, liquidity, Kelly). Rejects on `kellyFrac ≤ 0` (negative EV) before applying `minQty` floor. Stop distance = `stopMultiple × earningsAdj × ATR` where `stopMultiple` comes from the current regime's `stopAtrMult` and `earningsAdj = 1.3` when `signals.pre_earnings_risk = true`. Same input → same output. |
| **Validator** | Schema + business rules; auto-repair loop (≤2 retries); HOLD recs use `requiredUnless` to skip target/stop/qty checks. |

Calibration feedback (recent hit rates by confidence band and regime) is fetched from `GET /api/learning/calibration` and injected into every Claude user message.

## Learning Loop internals (the trade-outcome feedback path)

This is the most subtle subsystem. A recommendation's life-cycle spans three files and the backend `ai_learning_events` table.

### Life-cycle of a learning event

```
analysis.js logRecsToLearningLoop()        → POST /api/learning/log   (event created, was_executed=0)
   │  (rec gains rec._learningId)
recommendations.js markExecuted()           → POST /api/learning/outcome (was_executed=1, + outcome if it closed)
   │  on full-position close, reconciles parent BUY/TOP_UP events too
performance.js syncClosedTradesToLearningLoop()  → batch backfill for legacy recs lacking a _learningId; writes _learningId back to original state.recHistory entry after each successful log so scheduleSave() persists it (prevents re-logging on next Sync)
   │
routes/learning.py  _calib_compute() / stats   → decay-weighted win rates fed back into the next prompt
```

### Gotchas specific to the Learning Loop

- **Per-entry outcome, not blanket.** When a position built from several BUY/TOP_UP parcels is closed by one SELL, each parcel's win/loss is judged against **its own** entry price. A TOP_UP bought above the eventual exit is a `loss` even if the overall position was green.
- **`exit_reason` is direction-aware** (see table). A profitable TRIM must not read as `stop_hit` just because the exit sits numerically below the (above-entry) stop. Backfill historical rows with the corrected logic if you change this function — `asx_trader.db` rows written before the fix are stale.
- **The helper is duplicated** in `recommendations.js` (loaded first) and `performance.js` (loaded second, so its copy wins at runtime). Keep both byte-identical, or a stale copy silently takes over. `test_detect_exit_reason_direction_aware` evaluates the real function from **both** files against fixed cases.

## How prompt caching works

`callClaude()` sends the system prompt with `cache_control: { type: 'ephemeral' }` so subsequent intraday calls hit Anthropic's prompt cache. The static `ANALYSIS_SYSTEM_PROMPT` is cached as the first block; optional modules (tax-loss harvest, regime-specific rules) are appended as a second **uncached** block so they don't bust the cache when they change per-call.

`prompt-modules.js → buildSystemArray(context)` assembles the `[{type, text, cache_control?}]` array.

## Gotchas / contracts to honor

1. **Ticker tickers can include digits.** `A2M`, `S32`, `MP1`, `360` are all valid ASX codes. Validator regex is `[A-Z0-9]{2,5}(\.AX)?`.

2. **`adv_20` ≠ share count.** It's `close × volume` (AUD). Use `volume_avg_20` for share counts; derive shares from `adv_20 / price` if necessary.

3. **Panic regime drops recs, doesn't just shrink them.** `applyRegimeModifiers()` sets `qty=0, _regimeBlocked='panic'`. `analysis.js` filters these out — don't surface them.

4. **HOLD recs don't need target/stop/qty.** The validator schema uses `requiredUnless: 'HOLD'`. New action types should follow this convention.

5. **`state.priceAlerts`, `state.watchlist`, and `state.savedScreeners` ARE persisted.** All three are in the save payload (`api.js`) and in `BLOB_KEYS` in `routes/portfolio.py`, and returned by `db_load`. Don't drop any from either side — this was a Sprint 5 bug where `watchlist`/`savedScreeners` were sent but silently discarded.

6. **Stop/target alerts fire once.** `_stopAlertedAt` / `_targetAlertedAt` on the rec acts as a one-shot. Re-arms only after price retreats >2% from the trigger.

7. **The HTML script order is fragile.** If you add a new module, append it after its dependencies. There's no ES-modules safety net yet.

8. **SQLite uses `synchronous=NORMAL` + WAL.** Fast and crash-safe (loses only uncommitted last-txn, never corrupts). Don't downgrade to `synchronous=FULL` without measuring.

9. **`db.get_db` is the single source of truth.** Don't open `sqlite3.connect()` directly. Every `routes/*.py` does `from db import get_db` at import time — meaning each module has its **own binding** of `get_db`. Tests patch ALL of them via `_install_in_memory_db()` in `test_app.py`. **When adding a new route blueprint, add its module name (`routes.alerts`, `routes.import_csv`, etc.) to that helper or tests will hit the real DB.**

10. **Render functions must be pure.** `renderPerformance()` previously mutated `state.recHistory` inside render; now reconciliation happens in `reconcileRecOutcomes()` called from `renderPerformancePage()` BEFORE the HTML build. Follow this pattern for new pages.

11. **The error boundary catches render exceptions.** `navigation.js → renderPage()` wraps the actual render in try/catch. If you see "Page crashed" in the UI, the previous page render threw — the stack is in `console.error`.

12. **API key never logged.** `saveStateToDb` explicitly skips `settings.apiKey`. If you add another secret field, do the same. Telegram `tg_token`/`tg_chat_id` are stored **server-side** in the `settings` table (not in the browser save payload) — don't move them client-side.

13. **`_detectExitReason` is direction-aware.** SELL/TRIM recs frame the stop *above* and target *below* entry (a bearish/exit thesis) — the inverse of BUY/TOP_UP. The comparisons flip on `action`. Always pass the rec's `action`. Forgetting this mislabels profitable trims as `stop_hit` and pollutes `failure_patterns`/`exit_reason_dist`.

14. **`_detectExitReason` lives in `js/utils.js` — do not redefine it in page files.** Hoisted in Sprint 43: the canonical copy is in `utils.js` (loads first); `recommendations.js` and `performance.js` both resolve it from the shared global at call time. If either page file accidentally re-introduces a local definition it will shadow the canonical copy and silently diverge. The Vitest tests (`detect-exit-reason.test.js`) assert that `utils.js` owns the definition and neither page file redefines it.

15. **`fetch_with_retry` is not the `ttl_cache`.** They're orthogonal: `ttl_cache` serves the cached result within TTL; `fetch_with_retry` retries the live call and falls back to `_last_good` only when the call keeps failing. Both can coexist on the same function — the cache returns early before a retry is needed.

16. **Broker CSV import returns SELL rows in `sells` array (not `skipped`).** *(Sprint 46)* `handleBrokerCSV()` shows a confirmation dialog for SELL rows; "Apply SELL imports" uses `matchSaleAgainstParcels()` (FIFO/LIFO per `state.cgtMethod`) and logs to `cgtDisposals` + `tradeJournal`. Tickers with no open parcels are skipped. Does not update `state.cash` (historical import).

17. **Drawdown monitor needs portfolio history.** `renderPerformance()` computes drawdown from `state.portfolioHistory`. If `portfolioHistory` has <2 entries (e.g. fresh install), no drawdown cards are shown — this is intentional, not a bug.

18. **Forming-bar guard drops today's ASX candle before 07:00 UTC.** `_drop_forming_bar(hist)` in `indicators.py` removes the last daily bar when `now_utc.hour < 7` AND the bar date matches today (UTC or AEST = UTC+10). This prevents incomplete intraday candles from inflating RSI/MACD during market hours. Called unconditionally in `analyse_ticker()` after every yfinance/Stooq fetch. Safe for historical dates (bar from yesterday or earlier is never dropped).

19. **Stooq fallback ticker format.** `_fetch_stooq_history` converts `BHP.AX` → `bhp.au` (strip `.AX`, lowercase, add `.au`). Do not pass the full Yahoo `.AX` symbol to Stooq — it will return an empty CSV silently. The function imports `_HTTP_SESSION` lazily from `core` to avoid circular-import issues at module load time.

20. **Stop-proximity alert is direction-aware.** `checkStopProximityAlerts()` checks `(price − stop) / price` for BUY/TOP_UP recs (stop below entry), and `(stop − price) / price` for SELL/TRIM recs (stop above entry). Threshold is `state.settings.stopProximityPct` (default 3 %). Set to 0 to disable. One-shot via `r._proximityAlertedAt`; re-arms when price retreats to 2× the threshold.

21. **`trend_signals` values must be cast to Python `bool`.** Pandas comparisons (`cp > sma_20.iloc[-1]`) return `numpy.bool_`, which Flask's JSON encoder rejects with `TypeError: Object of type bool is not JSON serializable`. The fix is in `indicators.py`: `"trend_signals": {k: (bool(v) if v is not None else None) for k, v in trend_signals.items()}`. Any new dict returned by `analyse_ticker()` that contains numpy scalars must go through `safe_float()`, `int()`, `bool()`, or a similar cast — never raw numpy.

22. **`syncClosedTradesToLearningLoop()` must write `_learningId` back to the original `state.recHistory` entry.** The function builds a `reconciled` array via `history.map(r => ({ ...r, ... }))` — each entry is a new spread object. If you set `r._learningId = res.id` only on the spread copy, `scheduleSave()` will persist the unchanged original (still lacking `_learningId`), and every subsequent Sync will re-log the same trade as a new event, inflating calibration stats. Always find the matching original: `const orig = state.recHistory.find(x => x.id === r.id); if (orig) orig._learningId = res.id;`

23. **`stk.quarterly_earnings` and `stk.earnings` are deprecated in yfinance ≥0.2.x.** Use `stk.earnings_history` instead (columns: `epsActual`, `epsEstimate`). The earnings calendar endpoint in `routes/market.py` was updated to use this API. Any new code consuming per-quarter EPS data should use `earnings_history`, not `quarterly_earnings`.

24. **`_calib_cache` is protected by `_calib_lock` (threading.Lock).** Any code that reads or writes `_calib_cache` in `routes/learning.py` must hold the lock. Compute expensive DB work outside the lock — only the dict read and the final write need to be inside `with _calib_lock:`.

25. **`minQty` floor must never run on a zero/negative pre-floor qty.** `computeTradeParams()` returns `{ok:false}` when `kellyFrac ≤ 0` before reaching the `Math.max(QUANT_CONFIG.minQty, …)` line — do not move that Kelly guard below the `minQty` floor. *(Improvements.md #1)* A second, broader guard covers the other constraints: `if (rawQty * volScalar <= 0) return {ok:false, ...}` runs immediately before the `Math.max(QUANT_CONFIG.minQty, Math.floor(rawQty * volScalar))` line — any of `qtyByRisk`/`qtyByPosition`/`qtyByLiquidity`/`qtyByKelly` computing to 0 (stop too tight, position too small vs ADV, etc.) must hard-reject, not get silently bumped to a forced 1-share trade by the floor. The original bug checked `qty <= 0` *after* the floor had already run, which is dead code (`Math.max(minQty, x)` with `minQty=1` can never be ≤0). When adding new sizing constraints, always combine them into `rawQtyBase`/`rawQty` *before* this check, never apply `minQty` first.

26. **`_sanity_check` runs after `_drop_forming_bar` in `analyse_ticker()`.** It drops bars with >25% single-day close move. Penny stocks (close < $0.50) are exempt. If a legitimate corporate event causes a large move, the bar will be dropped and the following bar's ATR/RSI will look unusual — this is intentional and preferable to letting a data error corrupt all downstream signals.

A 55% sector reads as strong in a 45% market and weak in a 65% market, so the calibration sector line (`SECTOR:NN%WR vs mkt MM% (±Xpp,n=…)`), the sector×regime block, and the `/api/learning/stats` `by_sector[].wr_vs_market_pp` all express the signed delta. 49. **Never run more than one server instance against `asx_trader.db` at the same time.** The 2026-06-20 WAL corruption incident (dozens of "invalid page number" errors under `PRAGMA integrity_check`, requiring manual rowid-bisection recovery) is suspected to have come from two concurrent writers — e.g. `python asx_server.py` and `python waitress_server.py` both running, or a stray leftover process from a crashed/Ctrl+C'd session — racing on the same WAL file, possibly compounded by an ungraceful kill mid-checkpoint. Two defensive guards now exist: (a) **Single-instance lockfile** — `_acquire_single_instance_lock()` in `asx_server.py`, called only from the `if __name__ == "__main__":` block (never at import time, so `test_app.py`'s `asx_server.init_db()` + `app.test_client()` pattern is unaffected). It writes the current PID to `asx_trader.lock` next to the DB; on startup, if a lockfile exists with a different, **live** PID (checked via `os.kill(pid, 0)` — raises `OSError` for a dead/nonexistent PID on both POSIX and Windows, raises nothing if alive), the new process refuses to start and exits with a CRITICAL log line. A stale lockfile (dead PID) is silently reclaimed. The check is deliberately **fail-open**: any ambiguity — unreadable/malformed lockfile, an unexpected (non-`OSError`) exception from the liveness probe itself — logs a warning and lets startup proceed rather than risk blocking a legitimate restart. The lockfile is removed via `atexit.register()` on clean shutdown (Ctrl+C/`SystemExit` included, since Python's default SIGINT handler raises `KeyboardInterrupt`); a hard kill (Task Manager, `Stop-Process -Force`, SIGKILL) leaves a stale lockfile behind, which the *next* startup correctly reclaims. (b) **Startup integrity check** — `quick_integrity_check()` in `db.py` runs `PRAGMA quick_check` (cheaper than full `integrity_check`, sufficient as a sanity probe) once at server boot, called right after `init_db()`/`backup_db()` in `asx_server.py`. It is **non-blocking** — a result other than `'ok'` logs a CRITICAL message (console + `ai_responses/server.log`) with recovery guidance, but never refuses to start (a false positive or a merely-slow check on a large DB would be its own incident). (c) **Recovery path**: backups are plain file copies living next to the DB itself as `asx_trader.db.bak-YYYYMMDD` (NOT a `backups/` subdirectory), written by `backup_db(keep=7)` in `db.py` on every server startup plus once per 24h via the `db-backup` daemon thread in `asx_server.py`; only the 7 most recent dated copies are kept. 79. **Trade Journal model for parcel splits/reclassification (replaces gotcha #77): every parcel has AT MOST ONE journal row, found by `parcelId`, updated in place — never duplicated.** Confirmed with the user via explicit worked examples after gotcha #77's design proved wrong in practice (every reclassify click was inserting a permanent new row). The model:
    - **Split** (`splitParcel()`, `js/portfolio-helpers.js`) keeps the PARENT parcel's number on the remainder (unchanged from gotcha #74/#75 — e.g. splitting P#35's 847 shares by 200 leaves P#35 at 647, creates a new P#36 for the 200) and immediately syncs the journal via `_splitParcelJournalRow(parentParcel, newParcel, newParcelFees)`: the parent's existing row (found via `_findParcelJournalRow(parentParcel.id)`) flips `action` from `'BUY'` to `'RECLASSIFY'` **right away, at split time** — not deferred until a later account change — because once a parcel has been divided it no longer represents one clean "bought and held" transaction; its `qty` is also updated to the new (reduced) `remainingQty`. A brand-new row is created for the new parcel: `action: 'BUY'`, `qty`/`entryPrice`/`fees` matching the split-off amount, `date` = the ORIGINAL parcel's purchase date (this isn't a new transaction), `parcelId`/`parcel: "P#<id>"` set so it's immediately reachable for the same update-in-place treatment later.
    - **Account change** (`setParcelAccount()`) calls `_syncParcelJournalRow(parcel, newAccount)`: finds the row via `_findParcelJournalRow(parcel.id)` and mutates `row.account = newAccount; row.action = 'RECLASSIFY';` **in place** — no new row, regardless of how many times the same lot is reclassified back and forth. `action: 'RECLASSIFY'` is sticky (once flipped, stays flipped) since the row no longer represents a single untouched buy-and-hold. Falls back to creating one row only for a legacy parcel that genuinely has none yet (pre-dating `parcelId` tracking).
    - **Status stays `'open'`** throughout — only `action` changes. The earlier `status: 'reclass'` value (gotcha #77) was removed entirely; don't reintroduce a parallel status track for this, `action` already carries the semantic.
    - **Net effect**: a ticker bought once, split into N lots, and reclassified any number of times ends up with exactly N journal rows (one per parcel), each showing its CURRENT account and an accurate `RECLASSIFY`/`BUY` action — not a growing audit log of every intermediate hop. This is a deliberate trade-off the user chose: journal cleanliness over granular move-by-move history. If per-move history is ever wanted again, it would need a genuinely separate mechanism (e.g. a `notes` append-log on the row, or a dedicated history table) — do not resurrect the per-move-insert design, it was explicitly rejected.
    - **The new split-off row INHERITS the parent row's provenance and technical data verbatim** — `recId`, `recExecuted`, `entrySignals`, `thesis`, `regime` are all copied from `_findParcelJournalRow(parentParcel.id)` rather than left null. This matters because `js/pages/journal.js`'s `_journalProvenanceBadge()` and the detail drawer's `source` label both key off `recId` being non-null: a null `recId` reads as `✋ Manual`/`"Manual entry"` even when the split-off lot is really the SAME underlying AI/day-trade transaction, just divided. Multiple journal rows sharing one `recId` is already an established pattern (gotcha #66 — a SELL spanning several parcels produces one row per parcel, all sharing the SELL's `recId`), so this isn't a new kind of link. `setParcelAccount()`'s in-place update path needs no equivalent fix — mutating only `account`/`action` on the existing row never touches `entrySignals`/`recId`/`thesis`, so they survive every subsequent reclassify automatically.
    - **Regime badge fallback fixed alongside this**: the journal table's regime badge was reading `matchedRec?.regime` only (`js/pages/journal.js`), with no fallback to the row's own `t.regime` — meaning ANY row without a resolvable `matchedRec` (manual trades, CSV imports, and these split/reclassify rows before recId-inheritance) silently showed no regime badge even though `t.regime` was correctly populated per gotcha #65. Now reads `matchedRec?.regime || t.regime`.

    - **Whipsaw / contradiction check.** `GET /api/learning/recent-rec?ticker=X` (action-agnostic, unlike `entry-context` which is BUY/TOP_UP-only) returns the single most recent logged rec for one ticker. `entrySignature(sig)` in `js/utils.js` ports `_entry_signature()` (`routes/learning.py`) verbatim — same field set (`rsi_14`, `bb_pct_b`, `px_vs_sma200`, `setup_score`, `macd_hist`), same format — so a comparable signature can be built client-side from `state.liveSignals[ticker]` (which doesn't carry `px_vs_sma200`/`setup_score` directly; both are derived the same way `logRecsToLearningLoop()` already derives them). `js/analysis.js`'s validator pipeline (right after the existing contradiction-flagging block) batch-fetches `recent-rec` for every ticker in the current batch, and flags (via `_ruleWarnings`, **never drops** — same flag-don't-drop philosophy as gotcha-documented elsewhere) any rec whose direction flipped (BUY/TOP_UP ↔ SELL/TRIM) vs. the prior rec within 10 days under a near-identical signature (≥4 of ≤5 tokens identical). Rides the existing "Failed N rule(s)" chip — no new UI needed. **Whipsaw context enhancement (current session):** before the `recs.map()` pass, a second `await Promise.all` batch pre-fetches `GET /api/learning/calibration?tickers=<tk>&days=180` for every unique ticker; the returned block is scanned for a per-ticker memory token (`TICKER:…` pattern) and appended to the whipsaw warning as `(historical: …)` so Claude sees not just "contradicts prior rec" but also any known performance context for that ticker.
    - **Lesson lifecycle scoring.** `trading_lessons` rows are injected forever once created, never retrospectively validated. `_compute_lesson_effectiveness(conn, min_n_after=5)` (`routes/learning.py`) reuses the *exact* ticker/sector/regime OR-NULL scope-matching pattern `GET /api/learning/lessons` already uses for live injection, but applies it retrospectively: win rate on matching closed trades *before* vs *after* the lesson's own `created_at`. `n_after < 5` → `insufficient_data: true` (not enough trades since creation to judge). Exposed via `GET /api/learning/lesson-effectiveness`, sorted worst-first (most negative `delta_pp`). `renderLessonsCard()` (`js/pages/learning.js`) fetches this alongside the lessons list and renders a chip per row (or "not enough data yet"). Purely additive — never changes which lessons match or inject; the user still prunes manually via the existing DELETE endpoint.
    - **Calibration trend over time.** `GET /api/learning/calibration-stats` previously recomputed Brier score fresh from the whole table on every call with zero history. New `calibration_snapshots` table (`db.py` `_SCHEMA` — brand new table, no `ALTER TABLE` migration needed) gets one row per calendar day, written lazily inside `learning_calibration_stats()` itself (`INSERT OR REPLACE`, `UNIQUE(snapshot_date)` makes repeated same-day calls idempotent rather than a separate scheduler thread). `GET /api/learning/calibration-trend` is pure read (last 180 days, chronological). `drawCalibrationTrendChart(canvasId, snapshots)` (`js/charts.js`) is a new small line-chart function — note the inverted color convention vs. every other chart here: Brier is lower-is-better, so declining gets the `--up` (green) colour and rising gets `--down` (red) — the opposite of a price sparkline's up=green. Still follows gotcha #39 (no hardcoded hex, `chartColor()` tokens only). Rendered by `renderCalibrationTrendCard()` in `js/pages/learning.js`, skipped entirely when fewer than 2 snapshots exist yet.
    - **News feed swap.** `oilprice.com/rss/main` (category `geopolitics`, verified reachable with the plain non-browser `ASXNewsScanner` UA) was added to `MARKET_FEEDS` in `news_engine.py` alongside the still-enabled `bbc_world` — oil/gas supply shocks move ASX's materials/energy weighting more directly than generic world news. The dead `reuters_au` entry (404 since Reuters shut down public RSS in 2020) was left in place, still `enabled: False`, as documentation rather than deleted. `js/pages/macro.js`'s `runMacroAnalysis()` raised the macro-brief news cap 8 to 12 and `days` 1 to 2 (slower-developing geopolitical stories don't always break within 24h, and this call runs only a few times/day so the token-budget pressure justifying tighter caps elsewhere is weaker here) — but did NOT add an impact-score fallback, despite that being floated as an option beforehand: an existing code comment (2026-06-25 call #10 review) documents that a score-based fallback was tried before and removed for inflating scores on portfolio-specific stock stories with zero macro relevance (the rubric's STEP 3 specificity bonus is skipped only for already-categorized macro/geopolitics articles, so a `sector`/`other`-tagged article scoring high is almost always exactly that kind of noise, not a mis-tagged macro story). Don't re-add a score fallback here without re-litigating that finding.

86. **Seven Learning Loop stat deepening features landed together — BUY/TOP_UP split, capital efficiency, ensemble divergence, MAE/MFE summary, cluster-loss calibration nudge, lesson-drag calibration nudge, and monthly digest reminder.** All additive; no schema changes; all 4 new stats fields are empty-safe (return `{}`/`[]`/nulls when no trades exist yet).
    - **BUY vs TOP_UP split.** `buy_vs_topup` field on `GET /api/learning/stats` — separate win rate, avg P&L, and avg hold for initial BUY entries vs TOP_UP position additions. Surfaced as a two-row table card on the Learning page. Use this to determine whether adding to winners is paying off or cannibalising the BUY win rate.
    - **Capital efficiency.** `capital_efficiency` field on stats — `avg_pnl_per_day` (realized % ÷ hold days) grouped by `primary_entry_driver`, min n=3. Sorted fastest→slowest. Answers "which setup style returns the most per day of capital deployed?" — matters more than raw avg P&L when comparing short-momentum vs long-fundamental holds.
    - **Ensemble divergence.** `ensemble_divergence` field on stats — aligned (AI confidence and indicator-composite within 10pp) vs diverged. If the aligned bucket consistently outperforms, size down when they diverge.
    - **MAE/MFE path quality.** `mae_mfe_summary` field on stats — avg MAE/MFE split by win/loss. Rendered on the Learning page with an inline interpretation: if winners' avg MAE is shallower than losers', stop placement is appropriate; if they're comparable, stops may be too tight or entries poorly timed.
    - **Cluster-loss nudge.** `⚠CLUSTER_LOSS` in `_calib_compute()` — see gotcha 85 table update and `_calib_compute()` key-functions entry above.
    - **Lesson-drag nudge.** `⚠LESSON_DRAG` in `_calib_compute()` — see key-functions entry above. Does NOT auto-delete lessons; purely advisory — the user decides whether to `DELETE /api/learning/lesson/<id>`.
    - **Monthly postmortem digest reminder.** `checkMonthlyDigestReminder()` in `js/scheduler.js`, called from `schedulerTick()` (fires once per calendar month). Checks `localStorage.lastPostmortemDigestDate` (set by `generatePostmortemDigest()` in `learning.js`) and `localStorage.lastPostmortemDigestClosed` (closed-trade count at last run). When ≥15 new closed trades have accumulated, posts a notification-bell item ("Monthly Postmortem Digest") pointing the user to Learning → Digest. Never fires before the first manual digest run (no `lastPostmortemDigestDate` = no reminder).

87. **`run_sync()`'s today-announcement PDF resolution must key off Sydney date, not UTC.** (`announcement_engine.py`) ASX announcement dates are Sydney-local, but UTC trails Sydney by 10-11h — so for roughly the first 10 hours of each Sydney day (midnight through mid-morning, i.e. pre-market through market open, exactly when most announcements land), `datetime.utcnow().date()` is still on *yesterday's* date. An exact-equality check (`ann_date == today_str`) built from that stale UTC date silently failed for today's own announcements during precisely those hours, skipping the `todayAnns.do` special-case PDF resolution (the only way to resolve MAP-system hex-filename PDFs — the fallback numeric Markit-derived URL doesn't work for those). Net effect: today's announcements were still *discovered* fine (`_is_recent()` elsewhere is a lower-bound-only check, immune to this), but their PDF text could silently fail to extract/classify during market hours. Fixed by using the existing `_sydney_now()` helper (already used elsewhere for this exact reason) instead of `datetime.utcnow()` for this one comparison. Scan lookback itself is user-controlled via the `1d/3d/7d/14d/30d` dropdown on the Announcements page (`state.announcements.syncDays`, default 3d) — separate from the feed's *display* window, which is hardcoded to `days=7` in both `js/pages/announcements.js` and the `GET /api/announcements` default, regardless of what lookback was used to sync.

88. **Paper/real trade firewall — the ONE invariant: a record is REAL only when `mode === 'real'`; everything else (explicit `'paper'`, missing, `null`) is PAPER and is excluded from ALL tax (CGT/EOFY), real-cash, and real-performance math.** Failing safe means a fake trade can never leak into tax records by omission. The single source of truth is `isRealTrade(x)` in `js/utils.js` (accepts a record `{mode}` or a bare mode string; `x.mode === 'real'`), mirrored server-side by `_is_real()` in `routes/portfolio.py`'s EOFY pack and `trade_mode == 'real'` checks in `routes/learning.py`. **STATUS: Stage 1 (foundation) shipped; Stage 2 (execution wiring) NOT done yet.**
    - **Data model:** `trade_journal.mode` + `ai_learning_events.trade_mode` columns (`db.py`); `mode` field on `state.tradeJournal[]`/`cgtParcels[]`/`cgtDisposals[]`/`recHistory[]` (blob/extra_json-carried); `state.paperCash` (separate simulated pool — real `cash` stays in the `cash` table) + `settings.paperStartCash` (default 100000). `paperCash` rides `BLOB_KEYS`; `mode` is in the `trade_journal` INSERT/SELECT (db_save/db_load, `routes/portfolio.py`) defaulting to `'paper'`, and in the `/api/learning/log` INSERT defaulting to `'paper'`.
    - **Gatekeeper:** `askTradeMode(summary)` in `js/utils.js` — a blocking modal returning a Promise<`'real'`|`'paper'`|`null`(cancel)> with NO default (user must choose deliberately, per explicit decision). NOT yet wired into the lodge paths — that's Stage 2.
    - **Firewall consumers wired in Stage 1:** EOFY tax pack (`/api/tax/eofy-pack`) filters disposals AND trade_journal to `mode=='real'`; the Journal page renders a `PAPER` badge on non-real rows (`js/pages/journal.js`); `_calib_compute()`'s `_weight()` applies a uniform 0.5× discount to non-real rows (correct: during a pure-paper phase the constant cancels out of ESS/weighted-WR ratios, so calibration behaves normally; once real trades mix in, paper contributes less weight so real dominates).
    - **One-time backfill:** `db.py init_db()` stamps every pre-feature `trade_journal`/`ai_learning_events` row `'paper'` once (guarded by the `blob_store.paper_backfill_done` flag), per the user's decision that all lodged trades so far were fake. NOTE: the backfill does DML then `PRAGMA wal_checkpoint(PASSIVE)` a few lines later — the checkpoint CANNOT run with an open write transaction on the same connection (`get_db()` uses deferred isolation → SQLITE_LOCKED), so the backfill block ends with an explicit `conn.commit()`. Any future write added to `init_db()` before the checkpoint must do the same.
    - **Stage 2 (TODO — the execution wiring):** thread the chosen `mode` from `askTradeMode()` through every lodge path (`markExecuted`, `addManualTrade`, `executeDayTrade`, `executeIntradayTrade`, `applyDrpEvent`, CSV import) into the journal/parcel/disposal/recHistory/learning records; make the portfolio/parcel layer mode-aware (the `(ticker, account)` keying in `applyBuyToPortfolio`/`applySellToPortfolio`/`matchSaleAgainstParcels`/`getParcelsForTicker`/`getPortfolioHolding` becomes `(ticker, account, mode)` — a paper sell must only ever match paper parcels, a real sell only real parcels); route paper cash to `state.paperCash` not `state.cash`; default the Portfolio/Performance/CGT displays to real-only with a paper toggle. Until Stage 2 lands, the invariant keeps everything safe (all current data reads as paper → nothing reaches tax) but new trades aren't yet mode-tagged at lodge time.
    - **Migration ops caveat (gotcha #49):** the `ALTER TABLE` for the two new columns needs an exclusive lock, so it applies on the next server startup with no other instance holding `asx_trader.db`. A running server blocks the migration — stop it, then restart to pick up the new schema + code.
