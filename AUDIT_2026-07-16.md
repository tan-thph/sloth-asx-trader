## A. Trade Journal & execution path

### F1 [HIGH] `.AX`-suffixed rec tickers corrupt the portfolio in `markExecuted()`

**Status: Resolved (2026-07-16).** Fix plan option 1 applied — `validateRec()` now
canonicalizes `.AX` off `ticker`/`alternativeTicker` right after schema validation
(js/response-validator.js), so every downstream consumer sees a bare ticker. Tests:
`tests/response-validator.test.js`.

**Files:** `js/response-validator.js:262`, `js/pages/recommendations.js:1974–2035`,
`js/portfolio-helpers.js` (`applyBuyToPortfolio`, `applySellToPortfolio`, `getPortfolioHolding`)

The validator's ticker pattern is `/^[A-Z0-9]{2,5}(\.AX)?$/` — a rec can legally arrive as
`CBA.AX`. Inside `markExecuted()`:

- The **account-resolution** step (line 1974) correctly uses `_normTicker()`.
- But `getPortfolioHolding(rec.ticker, …)` (line 1996), `applySellToPortfolio(rec.ticker, …)`
  (line 1999), and `applyBuyToPortfolio(rec.ticker, …)` (line 2032) all pass the **raw** ticker.
  `getPortfolioHolding` only uppercases; it never strips `.AX`.

**Failure scenarios:**
- **SELL/TRIM `CBA.AX`** while holding `CBA` → holding lookup fails → `_executionFailed`
  ("no position found") even though the position exists. Annoying but safe.
- **BUY/TOP_UP `CBA.AX`** → creates a **brand-new holding row and CGT parcel under ticker
  `CBA.AX`**, separate from the real `CBA` book. Cash is debited, the phantom holding never
  matches liveSignals (`state.liveSignals['CBA.AX']` doesn't exist for portfolio fetches keyed
  bare), prices never refresh, and a later SELL of `CBA` can't consume the `.AX` parcel.
  This is silent book corruption.

Downstream, `_splitRecsByParcels` (analysis.js:2082) and `_dtSyncFromPortfolio`-style code
normalize independently, so the inconsistency only bites at execution time.

**Fix plan (pick one, prefer the first):**
1. Normalize at the source: in `js/response-validator.js`, after schema validation passes,
   canonicalize `rec.ticker = rec.ticker.replace(/\.AX$/i, '').toUpperCase()` (and the same for
   `alternativeTicker`). One site fixes every consumer — quant engine, `_splitRecsByParcels`,
   liveSignals lookups, execution, learning-loop logging.
2. Or defensively: `rec.ticker = _normTicker(rec.ticker)` at the top of `markExecuted()`.
   Narrower; leaves prompt-side lookups (`state.liveSignals[r.ticker]` in analysis.js
   post-processing) still missing for `.AX` recs.

**Test:** Vitest — feed `validateRec` a rec with ticker `BHP.AX`, assert the returned rec's
ticker is `BHP`; and an integration-style test that `markExecuted` on a `CBA.AX` BUY creates a
parcel with ticker `CBA` (mirror in `tests/response-validator.test.js` +
`tests/analysis-pipeline.test.js`).

### F2 [LOW] Rolling back a no-parcel SELL leaves a phantom CGT disposal

**Status: Resolved (2026-07-16).** The avg-cost fallback disposal now gets a stable
`id` (`_disposalIdBase + disposals.length`, same scheme as the parcel-matched loop)
so `rollbackTradeJournalEntry()`'s `disposalIds` branch fires. Test:
`tests/paper-real-firewall.test.js`.

**Files:** `js/portfolio-helpers.js:623–648` (fallback disposal), `:885–907` (rollback)

The avg-cost fallback disposal built when no parcels match (`matchSaleAgainstParcels`,
"No parcel — used avg cost basis") has **no `id` field** — the stable-id base is only applied to
parcel-matched disposals. So the journal row's `disposalIds` is `undefined`
(`d.id != null ? [d.id] : undefined` in `buildDisposalJournalEntries`). When
`rollbackTradeJournalEntry()` later reverses that SELL it restores the holding and cash but the
`disposalIds` branch is skipped — the disposal row **stays in `state.cgtDisposals` forever**,
double-counting the (possibly real) gain in the CGT liability summary and EOFY pack.

**Fix plan:** give the fallback disposal an id too (`_disposalIdBase + disposals.length`, same
scheme as the loop above it). That alone makes rollback symmetrical.
**Test:** Vitest — sell a ticker with zero parcels, roll the journal row back, assert
`state.cgtDisposals` is empty again.

### F3 [LOW] BUY rollback doesn't clean up linked day-trade positions

**Status: Resolved (2026-07-16).** `rollbackTradeJournalEntry()` now captures the
removed parcel and calls `_removeIntradayPositionForParcel()` /
`_removeSwingPositionForParcel()` (typeof-guarded) after removing it. Test:
`tests/paper-real-firewall.test.js`.

**File:** `js/portfolio-helpers.js:841–863`

Rolling back an open BUY removes the parcel (`state.cgtParcels.filter(p => p.id !== t.parcelId)`)
but never checks `state.intraday.openPositions` / `state.dayTrading.recommendations` for a
position carrying that `parcelId` (the 1:1 link gotchas #75/#78 maintain everywhere else). An
orphaned position survives pointing at a deleted parcel.

**Fix plan:** after removing the parcel, call `_removeIntradayPositionForParcel(p)` and
`_removeSwingPositionForParcel(p)` (existing helpers; guard with `typeof` like
`setParcelAccount` does).
**Test:** rollback a BUY whose parcel is linked to an intraday position → position gone.

### F4 [MEDIUM] `_splitRecsByParcels()` is mode-blind — SELL/TRIM cards blend real + paper lots

**Status: Resolved (2026-07-16).** Mirrors the existing account guard: scopes by
`state.portfolioViewMode` when it's `'real'`/`'paper'`, else by the ticker's single
holding mode, else skips splitting when both books hold it. Tests:
`tests/analysis-pipeline.test.js`.

**File:** `js/analysis.js:2075–2135`

The per-parcel split filters open parcels by **ticker + account only**. A ticker held real AND
paper in the same account (explicitly supported — `UNIQUE(ticker, account, mode)`, gotcha #91)
gets its SELL rec split across **both books' parcels**: per-lot qty, cost basis, unrealised
P&L, CGT eligibility and `_parcelId` can reference a paper lot on a card the user executes as
real (or vice versa). The account ambiguity is already handled (skip splitting when 2+
accounts) — mode needs the same treatment.

**Fix plan:** mirror the account guard. Compute `_holdingModes` for the ticker; if exactly one
mode holds it, filter parcels to that mode; if both, **skip splitting** (leave the rec unsplit,
same conservative fallback as multi-account). Optionally scope by
`state.portfolioViewMode` when it's 'real' or 'paper' (the analysis was run against that book
anyway, since `mergedPortfolio()` is view-scoped).
**Test:** Vitest in `tests/analysis-pipeline.test.js` — ticker with 1 real + 1 paper parcel,
SELL rec → assert not split / only same-mode parcels consumed.

## D. Learning loop

### F8 [MEDIUM] `ai_learning_events.timestamp` is UTC; every window/cutoff is Sydney-local — systemic ~10–11 h skew

**Status: Resolved (2026-07-16).** Added `_cutoff(days)` (UTC, space-separated —
matches storage) and `_fetch_retry_cutoff()` helpers in routes/learning.py; every
`timestamp`-comparing cutoff and every `fetch_failed_at`/decay/flip age calc now
routes through them (including `_mark_fetch_failed`'s write side, kept in lockstep).
Day-granular display-only dates (calendar snapshots, month scopes) deliberately
left on local time per the fix plan. Tests: `TestAuditF8UtcCutoffs` in test_app.py.

**Files:** `db.py:140` (`DEFAULT CURRENT_TIMESTAMP` — UTC, space-separated),
`routes/learning.py` (many sites: 1070, 3373, 3576, 3710, 4284–4285, 5448, …)

The learning-events INSERT (learning.py:1084) omits `timestamp`, so SQLite's
`CURRENT_TIMESTAMP` (UTC) applies. But **every** cutoff/window in learning.py is computed from
`datetime.now()` (machine-local = Sydney, UTC+10/11). Consequences, each small but systemic:

- The 7-day HOLD dedupe window, the 25/30-day resolver age gates, `?days=N` filters, decay
  weighting, cluster-loss "5d" windows and calibration recency are all shifted ~10–11 h.
- Worse, cutoffs built with `.isoformat()` carry a `'T'` separator while stored timestamps use
  `' '`. In lexical comparison `' ' < 'T'`, so on the **boundary day** every stored row
  compares as "earlier" than any same-day `T`-cutoff — windows silently gain/lose a boundary
  day depending on comparison direction. (Line 1070 already does it right:
  `strftime("%Y-%m-%d %H:%M:%S")`.)

**Fix plan (small, mechanical):**
1. Add a module helper in learning.py:
   `def _cutoff(days): return (datetime.utcnow() - timedelta(days=days)).strftime("%Y-%m-%d %H:%M:%S")`
   and replace every `datetime.now() … .isoformat()` cutoff with it (UTC to match storage,
   space separator to match format). Grep list: lines 1070, 3373–3374, 3576–3577, 3710–3711,
   4284–4285, 5448, 5646 + any `fromisoformat(ts)` age math (4313, 4340 — these parse stored
   UTC timestamps then subtract local `now()`; switch to `utcnow()`).
2. Do **not** migrate stored data — it's already consistently UTC; only the comparison side is
   wrong.
3. Leave user-facing date displays as-is (they're day-granular).

**Test:** unit test in `test_app.py` — insert an event stamped "now UTC", assert a
`days=0`-boundary window includes/excludes it correctly around the Sydney/UTC offset.

## F. Cross-cutting / housekeeping

### F12 [LOW] Critical price-decline alert: dismissal re-arm logic is inverted

**Status: Resolved (2026-07-16).** Flipped to `prev.pct <= alert.pct`. Removed the
dead `state.dismissedAlerts` write (confirmed nothing ever read it) instead of
wiring it up — no consumer needed it. Tests: `tests/paper-real-firewall.test.js`.

**File:** `js/portfolio-helpers.js:74–83`

`dismissed: prev?.dismissed && prev.pct >= alert.pct` — pct values are negative. If the decline
**worsens** (alert.pct more negative), `prev.pct >= alert.pct` is TRUE → stays dismissed
(comment says it should re-surface). If it **improves**, the alert un-dismisses and reappears.
Exactly backwards. Also `dismissCriticalAlert()` writes `state.dismissedAlerts[ticker]` which
nothing ever reads (dead state).

**Fix:** flip to `prev.pct <= alert.pct` (stay dismissed unless the decline deepened), and
either use or delete `state.dismissedAlerts`.
**Test:** Vitest — dismissed at −16%, new pass at −18% → visible again; at −12% → stays
dismissed.

### F13 [LOW] `db_save` journal loop can 500 the whole save on one malformed row

**Status: Resolved (2026-07-16).** Required fields (`ticker`/`action`/`qty`/
`entryPrice`) are validated BEFORE the `DELETE FROM trade_journal`; a malformed row
is skipped and logged via `current_app.logger.warning()`, not crashed. Tests:
`TestSprint5.test_db_save_skips_malformed_journal_row_instead_of_500ing`.

**File:** `routes/portfolio.py:127–155`

`t["ticker"] / t["qty"] / t["entryPrice"]` are bare indexing — one malformed client row throws
KeyError → the entire bulk save 500s *after* `DELETE FROM trade_journal` ran… inside the same
transaction, so SQLite rolls back (the `with get_db()` context) — no data loss, but the app
enters persistent-save-failure territory (its known worst failure mode, gotcha #91). Cheap
hardening: `.get()` with a skip-and-log for rows missing required fields, or validate before
the DELETE.

### F14 [LOW] `has_data` ignores blob-only state

**Status: Resolved (2026-07-16).** `has_data` now also counts non-empty
`cgtParcels`/`cgtDisposals`/`portfolioHistory` blobs (settings deliberately still
excluded — 2026-07-07 self-perpetuating-wipe guard). Tests:
`TestSprint5.test_has_data_true_for_blob_only_state` /
`test_has_data_false_when_everything_is_empty`.

**File:** `routes/portfolio.py:329`

`has_data = bool(portfolio or trade_journal or rec_history)` — a DB whose only real data is in
blobs (cgtParcels, disposals, portfolioHistory, watchlist) reports `hasData: false`, letting a
fresh client treat it as empty. Consider including `cgtParcels`/`cgtDisposals`/
`portfolioHistory` presence.
